## Where the two backends genuinely differ

### Partition polling

The in-process log exposes `poll(partition)`: the caller names the
partition it wants, because there is no coordinator to negotiate with.
Kafka's group coordinator **assigns** partitions to members — a
consumer subscribes and is told. Asking for a specific partition means
leaving the group and assigning manually, which gives up rebalancing,
liveness detection, and every other reason to use a consumer group.

So `src/backend.py` exposes the **intersection**, `drain_all()`, and
not the union. Per-partition polling stays on the backend where it is
real. The alternative — emulating it on Kafka by filtering the
assignment — works with one consumer and is wrong the moment there are
two, which is exactly when it would matter.

### Record order

| backend | drained records arrived grouped by partition |
|---|---|
| file | yes |
| kafka | yes |

**This row flips between runs, and that is the finding.** On the
same recording, the same broker and the same code, a Kafka drain
has been observed both grouped by partition and interleaved; this
run came back **grouped**.

The first version of this document asserted Kafka always
interleaves. The first run said grouped, which looked like a
correction to make — a topic this small fits in one or two fetches,
so the drain appends one partition's batch at a time and the result
looks ordered. The next run interleaved. Neither observation was
the rule; the variation is.

So the honest statement is the contract, not the observation:
**Kafka guarantees per-partition order and nothing more.** Code
relying on the grouping that shows up on small data passes every
test written against small data and breaks at volume, which is the
worst available failure schedule. The file backend drains
partition-by-partition and is deterministic — which makes it the
more forgiving of the two, and therefore the one that lets a
latent ordering assumption survive to production.

What both backends *do* guarantee: a key lands in one partition and its
records come back in order. This project's bars are safe under either
because they sort by event time within each symbol — which was true by
accident before it was true on purpose.

### Partition assignment — and the claim it refuted

| backend | symbol -> partition |
|---|---|
| file | BTC/USD=0, ETH/USD=0 |
| kafka | BTC/USD=1, ETH/USD=3 |

**The two backends put the same key in different partitions,**
and this document asserted the opposite until the run said
otherwise. 2 of 2 symbols map differently.

The in-process log hashes with its own stable function; Kafka
uses **murmur2**, the partitioner every Kafka client
implements. Both are stable across restarts — which is the
property that actually matters, and the reason neither uses
Python's `hash()`, randomised per process, which would move a
symbol on restart and break its ordering silently.

But they are not the SAME stable function, and three things
follow that are easy to get wrong:

- **Committed offsets do not port.** An offset is a position
  in a partition. Migrating a consumer group between these
  backends cannot carry offsets across, because partition 2
  does not hold the same keys on both sides.
- **Any hardcoded key-to-partition mapping breaks.** Anything
  of the form "BTC/USD is partition 0" is backend-specific
  even though both are "partitioning by symbol".
- **Skew differs.** On this run the file log put every symbol
  in ONE partition while Kafka spread them across two. Same
  keys, same partition count, different parallelism ceiling.
  With few keys, which hash you use is a capacity decision.

No symbol appears in more than one partition on either backend,
which is what makes the per-key ordering guarantee mean anything.
Checked here rather than assumed.

## What this still is not

- **One broker.** Replication, leader election and an in-sync-replica
  shrink are the failures that actually take a stream down, and none of
  them is reachable with a single node. `acks=all` against one broker
  is a weaker promise than it looks.
- **One consumer per group.** The coordinator's whole job — rebalancing,
  detecting a dead member, reassigning its partitions — needs at least
  two members to observe. The asymmetry described above is the *reason*
  for the interface, but the rebalance itself is unobserved here.
- **No exactly-once.** Commit happens after processing, which is
  at-least-once. Transactional produce plus `read_committed` is a
  different mechanism and is not used.
